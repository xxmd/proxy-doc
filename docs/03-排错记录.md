## 坑 1：`www.microsoft.com` 不能做 REALITY 的 target ⭐

**现象**：服务端配置校验通过、服务正常监听 443、密钥对校验也匹配，但任何客户端（Xray 客户端、mihomo）连上去都是：

```
客户端：failed to find an available destination > common/retry: [EOF]
服务端：REALITY: processed invalid connection from x.x.x.x:xxxxx: handshake did not complete successfully
```

**排查过程**：

1. 先确认不是密钥问题 —— `xray x25519 -i "<私钥>"` 反推出的公钥与客户端填的完全一致 ✅
2. 确认不是服务端转发问题 —— `curl --resolve www.microsoft.com:443:127.0.0.1 https://www.microsoft.com` 返回 **200 + 证书校验通过**，说明未认证流量的转发是好的 ✅
3. 于是怀疑 target 本身，做了**候选站矩阵测试**

**结果**：

| target | 结果 |
|---|---|
| `www.microsoft.com` | ❌ 失败 |
| `www.apple.com` | ✅ 200 |
| `www.cloudflare.com` | ✅ 200 |
| `www.amazon.com` | ✅ 200 |
| `www.lovelive-anime.jp` | ✅ 200 |
| `www.hkex.com.hk` | ✅ 200 |

**结论**：换成 `www.hkex.com.hk` 后立刻全通。

**原因推测**：`xray tls ping www.microsoft.com` 显示它启用了 **X25519MLKEM768** 后量子密钥交换：

```
TLS Version:                    TLS 1.3
TLS Post-Quantum key exchange:  true (X25519MLKEM768)
```

Xray 官方文档提到「如果 target 支持 X25519MLKEM768，REALITY 客户端也会自动使用该后量子算法进行密钥协商」，微软的 TLS 栈在这个交互上和 REALITY 服务端不兼容。

**教训**：
- **换 target 前一定要先用 `xray tls ping <域名>` 预检**，并跑一遍 `test-reality-targets.sh` 做端到端实测
- 挑 target 的原则见 `../server/README.md`

> 📌 **2026-10-30 补记（重要）**：上面「原因推测」那段现在看**靠不住**。
> 后来读了 `xtls/reality` 的源码才发现，**X25519MLKEM768 是服务端要求客户端带的**（新版 REALITY 强制 ClientHello 里必须有这个后量子
> 密钥协商），跟 target 支不支持后量子**没有关系**；target 只影响"握手时去它那儿借证书"这一段。
> 所以当年 `www.microsoft.com` 失败的真实原因还没查清（有可能是当时客户端指纹/utls 的问题），
> 但**结论仍然有效**：`www.hkex.com.hk` 一直很稳，继续用。详见坑 10。

## 坑 2：TUN 模式让所有网络测量失真

**现象**：测本地到服务器的延迟，`ping` 显示 30–55ms，但 `TcpClient` 握手只要 **1–2ms**。上海到香港不可能 1ms。

**原因**：Clash Verge 开着 **TUN 模式**：

```
Meta (Meta Tunnel)  Up  100 Gbps          ← TUN 虚拟网卡
默认路由 0.0.0.0/0 → 198.18.0.2 via Meta (metric 0)   ← 抢占了物理网卡的路由
```

TUN 会**在本地接受 TCP 连接**再转发，所以任何 `TcpClient.Connect()` 都是瞬间完成，测出来的是"连本地虚拟网卡"的时间。

**更坑的一点**：TUN 里的流量还会被 Clash 的 **sniffer 嗅探**。当我在本地起第二个 mihomo 实例去连 REALITY 服务器时，Clash 嗅探到 ClientHello 里的 SNI 是目标大站域名，**"帮忙"把连接重定向到了真的目标站**，导致 REALITY 握手被对方踹掉（`connect error: EOF`）。所以那次测试的失败**不是服务端的问题**。

> 📌 **2026-10-30 补记**：TUN 确实会让测量失真，但它**不是** Clash Verge 里 `HK-Reality` 一直 Timeout 的原因。
> 真正的原因见下面的「坑 10」（mihomo 的 REALITY 认证被新版 Xray 服务端拒绝）。
> 关掉 TUN 之后 Timeout 依然存在，就是最好的反证。

**怎么判断**：

```powershell
Get-NetRoute -DestinationPrefix '0.0.0.0/0' | Select-Object NextHop,RouteMetric,InterfaceAlias
Get-NetAdapter | Select-Object Name,InterfaceDescription,Status
```

看到默认路由指向 `Meta` 之类的虚拟网卡，就是开着 TUN。

**怎么绕过**（三选一）：

| 方法 | 做法 |
|---|---|
| 关 TUN（最简单） | Clash Verge 里关掉 TUN 模式和系统代理再测 |
| 加 /32 直连路由 | `route add <IP> mask 255.255.255.255 <网关> metric 1 if <网卡索引>`（需管理员；最长前缀匹配必定赢过 /0 默认路由） |
| 换测量点 | 在服务器本机跑一个客户端实例自测（`xray-verify.sh` 就是这么做的） |

**教训**：**测量前先确认测量链路是干净的。** 这次如果没有发现这个矛盾，会一直在错误的方向上调服务端。

## 坑 3：机场的「多国节点」大部分是假的

对一个机场做了 36 节点的落地探测（`client/bench-nodes.ps1 -GeoOnly`），结果：

```
36 个节点 = 36 个不同出口 IP，但只有 10 个 ASN
其中 25 个（69%）来自同一家 ASN（AS38136 Akari Networks）
同地区的 5 个节点，出口 IP 是同一段里的连号地址
```

| 地区 | 出口 IP 段 | ASN | 上海直连物理 RTT |
|---|---|---|---|
| 香港 ×5 | `188.253.115.11–15` | AS38136 Akari | ICMP 被禁 |
| **台湾 ×5** | `185.220.236.2–6` | AS38136 Akari | **290–337 ms ⚠️** |
| 新加坡 ×5 | `188.253.121.25–29` | AS38136 Akari | ICMP 被禁 |
| 日本 ×5 | `185.220.239.50–54` | AS38136 Akari | 84–92 ms |
| 美国 ×5 | `5.34.216.210–214` | AS38136 Akari | 138–164 ms |
| 韩国 ×1 | `3.34.227.181` | **AS16509 Amazon AWS** | 187 ms |
| 德国 ×1 | `45.77.55.181` | **AS20473 Vultr** | 206 ms |
| 菲律宾 ×1 | `2a09:bac5:…` | **AS13335 Cloudflare WARP** | — |

**关键结论**：

1. **「台湾节点」是假落地** —— TCP 握手实测 292ms（ICMP 290ms，两者一致排除了限速干扰）。台北到上海物理上不可能超过 60ms。
2. **「5 个节点」= 同一段连号的 5 个 IP**，性能几乎一样，**在它们之间切来切去等于没切**。
3. **部分「国家节点」是租的廉价 VPS**：韩国 = AWS EC2，德国 = Vultr，菲律宾 = Cloudflare WARP。
4. 判读假落地要 **`colo` + 物理 RTT 一起看**，单看一个会误判（例如马来西亚节点 `colo=SIN` 是正常的 —— 新山离新加坡只有 20km；而菲律宾节点 `colo=HKG` 就是真·假落地）。

**方法论**：`client/bench-nodes.ps1` 就是为这个写的，三个数据源互相印证：
- `api.ip.sb/geoip` → 出口 IP / ISP / ASN
- `cloudflare.com/cdn-cgi/trace` 的 `colo` → 离出口最近的 CF 机房（最硬的证据）
- 直连 ping 出口 IP → 物理 RTT

## 坑 4：入口线路差不是换节点能解决的

对同一台机场入口做逐跳定位：

| 跳 | IP | 归属 | RTT | 丢包 |
|---|---|---|---|---|
| 1 | 192.168.1.1 | 本地路由器 | 0ms | 0% |
| 2 | 180.165.56.1 | 电信上海（AS4812） | **2ms** | 0% |
| 8 | 183.91.56.126 | AS4134 电信国际出口 | **100ms** | 16% |
| 14 | 机场入口 | AS401984（香港） | **106ms** | 13% |

**慢在电信的国际出口那一跳就已经产生了**，怀疑路径绕经新加坡再转 NTT 回香港。

配合 TCP 握手测到的 **1120ms 尖峰**（典型的 SYN 重传 ≈ 1 秒 RTO），确认存在 **5–13% 真实丢包**。

**教训**：
- 这个 106ms + 10% 丢包是**所有节点的共同地板**，换节点、换落地国家都突破不了
- 这种丢包率下，**TCP 系协议（AnyTLS/Trojan/REALITY）都会被严重拖累**，QUIC 系（Hysteria2）才是对症的
- 判断线路好坏要看**逐跳定位**，而不是看机场宣传的"CN2 直连"

## 坑 5：Xray 安装脚本缺少依赖 / geo 资源路径

| 问题 | 现象 | 解决 |
|---|---|---|
| 缺 `unzip` | 官方安装脚本报 `Installation of unzip failed` | 先 `apt-get install -y unzip` |
| `XRAY_LOCATION_ASSET` 未设置 | `geoip:cn` / `geosite:cn` 规则找不到数据文件 | 加 systemd drop-in 指向 `/usr/local/share/xray` |
| 日志目录权限 | 服务以 `nobody` 运行，写不进 `/var/log/xray` | `chown -R nobody:nogroup /var/log/xray` |
| 日志「消失」 | 配置里只写 `loglevel` 不写 `error` 路径时，日志去了 stdout（journald），`tail` 文件看不到 | 要么指定路径，要么用 `journalctl -u xray` 看 |

## 坑 6：配置文件编码导致 PowerShell 脚本报错

**现象**：脚本在 Windows PowerShell 5.1 下报一堆诡异的语法错误（`Missing expression after ','`），但文件内容看起来完全正常。

**原因**：PS 5.1 读取**无 BOM 的 UTF-8** `.ps1` 文件时，会按系统 ANSI 代码页（中文系统是 GBK）解码。中文注释的 UTF-8 字节被当 GBK 解析，可能"吃掉"后面的换行符，导致语法崩溃。

**解决**：写文件时加 **UTF-8 BOM**：

```powershell
$txt = [System.IO.File]::ReadAllText($path, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($path, $txt, (New-Object System.Text.UTF8Encoding($true)))
```

**同理**：通过 `pwsh -Command` 传递含中文的命令行时，PS 5.1 也可能按 GBK 解码导致乱码 —— 把脚本写成文件再执行，不要在命令行里塞中文。

## 坑 8：mihomo 内置的 `GLOBAL` 组会骗你

**现象**：用脚本逐节点探测时，36 个节点的出口 IP **全部相同**，看起来像是"整个机场都是假落地"。

**真相**：脚本自动选中了 mihomo 内置的 **`GLOBAL`** 组，但在 `mode: rule` 下**切换 GLOBAL 不影响实际流量**（流量走的是规则里指定的组）。所以所有请求都从同一个节点出去，得到同一个出口 IP。

**验证方法**：把 `GLOBAL` 设成 `DIRECT`，如果出口 IP 不变，就说明它没在生效路径上。

**正确做法**：
1. `GET /rules` 看规则实际指向哪个组
2. `PUT /proxies/<那个组>` 才是有效切换

`client/bench-nodes.ps1` 已经修掉了这个 bug：自动选组时排除 `GLOBAL`，优先选规则真正引用的组，选不中会打警告。

## 坑 10：mihomo 的 REALITY 握不上新版本 Xray 服务端 ⭐⭐

**现象**：Clash Verge 里 `HK-Reality` 节点永远是 `Timeout`。同一台电脑上：

- `ping` / TCP 连 `服务器:443` 正常（112 ms）；
- 订阅 URL 返回 200，配置内容和服务端完全对得上；
- 服务端 error.log 里除了启动那行以外**什么都没有**（因为 `loglevel: warning` 把关键日志滤掉了）；
- **用 Xray 官方客户端连同一个节点，秒通**；
- **用 mihomo 连，必挂**。

**mihomo 的报错**（`log-level: debug`）：

```text
REALITY localAddr: x.x.x.x:443 is using X25519MLKEM768 for TLS' communication: false
REALITY Authentication: false, AEAD: *gcm.GCM
[TCP] dial HK-Reality ... error: x.x.x.x:443 connect error: REALITY authentication failed
```

**把服务端 `log.loglevel` 改成 `info` 后**，服务端说的是：

```text
[Info] transport/internet/tcp: REALITY: processed invalid connection from 180.165.59.38:64100:
       authentication failed or validation criteria not met
```

**这两个日志合起来就说明白了**：请求到了服务器，但服务端**不认这个客户端**，把它当成"探测流量"原样转发给真实网站
（`www.hkex.com.hk`），客户端收到真证书 → 校验不过 → 报 `REALITY authentication failed` → 界面上显示 `Timeout`。

**根因**：Xray 从 2026 年年中开始给 REALITY 服务端加了两道闸门，而 mihomo 一个都过不去。

| 闸门 | 起始版本 | 服务端校验内容 | 有没有开关 |
|---|---|---|---|
| ① `minClientVer` 默认为 `26.3.27` | **v26.7.11**（v26.9.9 起又被注释掉） | REALITY 认证包里有 3 字节客户端版本号。**mihomo 硬编码上报 `1.8.2`**（它内核里对标的还是 Xray v1 时代），低于 26.3.27 直接判非法 | 有：`"minClientVer": "0.0.0"` |
| ② ClientHello 必须带 `X25519MLKEM768` | **v26.9.9**（reality 模块 2026-09-08） | `xtls/reality` 的服务端代码里，如果 key_share 里只有纯 X25519、没有后量子混合的 X25519MLKEM768，会直接 `break`——**连认证解密的代码都进不去** | **没有**，写死 |

`xtls/reality` 服务端源码（`tls.go`）里那道硬闸门：

```go
var peerPub, peerPub2 []byte
for _, keyShare := range hs.clientHello.keyShares {
    if keyShare.group == X25519MLKEM768 { peerPub2 = keyShare.data[mlkem.EncapsulationKeySize768:] }
    if keyShare.group == X25519        { peerPub  = keyShare.data }
}
if peerPub2 == nil {
    // 只有纯 X25519 → 直接放弃认证
    break // reject outdated/strange Client Hello that doesn't have X25519MLKEM768 before optional X25519
}
```

对比 2026-03 的旧版 reality 模块，那时是先找 X25519、找不到才退而求其次找 X25519MLKEM768 里的那段 X25519
（`if peerPub == nil { ... }`），所以老服务端对 mihomo 是友好的。

**本地 A/B 实测**（同一台 Windows，同一个 mihomo，本地起不同版本的 Xray 服务端，密钥/UUID/target 全一样）：

| 服务端 Xray | `minClientVer` | mihomo 结果 | 服务端看到的 ClientVer |
|---|---|---|---|
| 26.6.27 | 无此字段 | ✅ 204 | `1.8.2` |
| 26.7.28 | 默认 26.3.27 | ❌ auth rejected | `1.8.2` |
| 26.7.28 | `"0.0.0"` | ✅ 204 | `1.8.2` |
| 26.9.9 | `"0.0.0"` | ❌ auth rejected | 看不到（解密前就被拒） |
| 26.10.29 | `"0.0.0"` | ❌ auth rejected | 看不到（解密前就被拒） |

结论：**mihomo（Clash Verge / Mihomo Party / FlClash / OpenClash）能用的最后一个服务端版本是 v26.7.28（且要改 `minClientVer`），
零改动的话是 ≤ v26.6.27。** 客户端那边没有可调项——mihomo v1.19.29 和最新的 v1.19.33 都一样，不是版本 bug，是它一直没跟进。

**两种解法**：

| 方案 | 做法 | 代价 |
|---|---|---|
| 服务端降级（当前选择） | 装 `v26.6.27` 的 `Xray-linux-64.zip`，`install -m 0755` 覆盖 `/usr/local/bin/xray`，重启服务。**配置一个字都不用改** | 少 4 个月的 Xray 更新，用不上新版 REALITY 的后量子认证/ML-DSA-65 |
| 客户端换内核 | 服务端保持最新，客户端换成 Xray 内核的（v2rayN / v2rayNG / NekoBox / Xray kit） | 要放弃 Clash Verge 那套订阅管理 |

**教训**：

1. **「服务端自测通过」不能证明「客户端能连」。** `xray-verify.sh` 用的是 Xray 自家客户端，它当然能过自家新加的闸门；
   要证伪「服务端有问题」，必须拿**真正要用的那个客户端**去测。
2. **两侧版本要一起看。** 代理协议本身（VLESS / Vision / REALITY 字段）没变，是**认证协议的实现细节**在演进，
   这类不兼容在配置层面完全看不出来——配置校验是 `Configuration OK`，服务端 `active`，端口也 `LISTEN`。
3. **`log-level: debug` / `loglevel: info` 是这次唯一真正有用的信息源。** 服务端在 `warning` 级别下那行
   `processed invalid connection` 根本不会出现（它是 `Info` 级别），这就是为什么 9 月那次什么都没查出来。
4. 出问题时先问一句：**「有没有一个能连通的对照客户端？」** 有对照，5 分钟定位；没有对照，就会一直在服务端和 TUN 之间来回猜。
